# GuardTowarr 2.0 operation and validation

## Multiple instances

Settings → Services → Add another service → choose the application → Add instance.
Give it a recognizable display name, address, and credentials. Credentials are not
copied from the original. Test the connection, then save. Removing an extra instance
only removes monitoring configuration; it never deletes the external application.
Default instances can be disabled.

Search has an instance selector. The add dialog keeps the selected instance even
if background polling updates the dashboard. Root folders and quality profiles
are validated against that instance before adding. Movies and shows can be added;
books and music remain explicitly search-only.

## SABnzbd

Use the full API key, not the NZB-only key. GuardTowarr reads `queue` and `history`;
it does not pause, delete, or retry SABnzbd jobs. Active entries include progress,
state, size, and ETA. Failures from the last 24 hours are shown as issues. If a
client cannot be reached, the combined downloads panel names the failed source
and retains results from sources that responded.

API reference: https://sabnzbd.org/wiki/configuration/5.1/api

## Cleanuparr

Enter the instance URL and its API key. GuardTowarr sends `X-Api-Key` and reads
`GET /health/detailed` and `GET /api/manualevents?isResolved=false`. It displays
health entries and the latest 100 unresolved events, with an overflow notice.
An older version without the events endpoint reports that limitation instead of
silently claiming complete health coverage. No cleanup or resolve API is invoked.

Contract references:

- https://github.com/Cleanuparr/Cleanuparr/blob/main/code/backend/Cleanuparr.Api/Controllers/HealthController.cs
- https://github.com/Cleanuparr/Cleanuparr/blob/main/code/backend/Cleanuparr.Api/Controllers/ManualEventsController.cs

## Docker monitoring

Enable Docker in Services. Use an HTTP(S) Docker socket proxy reachable from
GuardTowarr, or `unix:///var/run/docker.sock` in a Linux deployment where that socket
is already mounted. Windows deployments can use an HTTP(S) proxy; Windows named
pipes are not implemented.

GuardTowarr only calls `GET /containers/json?all=1`. Configure a proxy to permit
that read endpoint and deny writes; do not publish the proxy port to the internet.
A raw Docker socket grants broad host control to any process that can access it,
even if the filesystem mount is marked read-only. The integration itself contains
no container start/stop/restart/delete actions. This update does not mount or expose
your socket automatically.

The optional comma-separated container filter uses exact container names, without
the leading slash. Blank means monitor every container, including intentionally
stopped ones; use a filter to exclude those. Selected containers disappearing also
produce an issue.

API reference: https://docs.docker.com/reference/api/engine/version/v1.51/

## Monitoring and actions

Health percentage is the proportion of observed time with an `ok` result. Warnings
and errors count as attention-needed time, and gaps longer than three polling
intervals (at least two minutes) are unobserved. No historic uptime is invented
for periods before this version started collecting observations.

An interrupted pending action may have reached the upstream service. Check that
service before retrying. Automatic blocked-file removal stays opt-in. Failed
blocklist lookups pause automation, and changing extension rules causes re-scanning.

Remote access retains the separate token-protected port and independent request
and action permissions. Internal root folders appear as `Root folder <ID>` remotely.
The admin port remains trusted-LAN-only. Treat media titles and viewing activity
as visible to anyone authorized to access the remote dashboard.

## Verification and release

Run from the project root:

```text
python -B -m unittest discover -s tests -v
python tools/check_frontend.py
python tools/release_version.py v2.0.0
python tools/preview.py
```

The preview uses temporary settings and simulated services at ports 19595/19596.
Its remote token is `preview-token`; it must not be deployed as a real instance.
The test suite uses temporary directories and loopback servers, never your config.

`build.bat` installs pinned optional build dependencies, runs checks, and builds the
Windows executable. CI runs Python checks on Windows/Linux and Python 3.12/3.13.
The release workflow belongs in `.github/workflows/release.yml`. It requires an
existing matching GitHub release and Docker Hub repository secrets. A manual run
checks out the requested tag rather than an arbitrary branch.

Stable release publication builds both Docker tags in the same operation and
compares their manifest contents. A release candidate publishes only its version
tag. The older root-level `docker-publish.yml` has been replaced by the active workflow.

Before promoting a candidate to stable, perform live-service checks for the
versions you deploy, including authentication failures, a deliberately stopped
test container, failed imports, notification delivery, and a backup/restore cycle.
Automated fixtures verify behavior but cannot establish compatibility with every
upstream version. Publishing credentials are not stored in this source tree.
